# Дообучение после SFT-only

> **Доступность:** scheduler-запускаторы ниже — локальные файлы кластера и в репозиторий не входят. Примеры с ними требуют отдельных запускаторов. Доступный Python runner — [`finetune_from_sft.py`](finetune_from_sft.py); используйте `--help` для списка параметров.

Эксперимент проверяет, сохраняется ли прирост от GFlow/CE после уже выполненного
SFT-only дообучения. Каждая ветка стартует из выбранного `best.pt` этого контроля.
Исходные веса и seed нового запуска всегда **42**; LR нового этапа — **3e-5**.
Дополнительная SFT-ветка показывает эффект ещё одного этапа обучения на тех же данных.

Каждый новый запуск SFT-only, GFlow и CE получает из исходного чекпоинта только
`model_state_dict`. AdamW создаётся заново, с пустыми моментами и нулевым счётчиком
обновлений; состояние optimizer, AMP и обучения исходного SFT-only не восстанавливается.
Это старт нового этапа обучения. Полный resume из `checkpoints/last.pt` относится
только к прерванной ячейке этого нового эксперимента, после проверки её источника
и настроек. Различие между загрузкой весов и восстановлением состояния optimizer
также описано в [документации PyTorch](https://docs.pytorch.org/tutorials/beginner/saving_loading_models.html#saving-loading-a-general-checkpoint-for-inference-and-or-resuming-training).

Аудит всех девяти исходных `best.pt` подтвердил **постоянный LR 3e-5**:
`scheduler_state_dict=None`, `trainer_config.scheduler_step_on="none"`,
LR во всех группах optimizer равен `3e-5`. Исходные SFT-only не использовали
warmup или decay. Поэтому во всех трёх новых ветках сохраняется тот же постоянный
LR и `scheduler=None`. Параметры AdamW: `betas=(0.9, 0.999)`, `eps=1e-8`,
`weight_decay=0.01`.

Batch size, accumulation, параметры validation и early stopping берутся из
исходного SFT-only протокола. Перед новым этапом всегда выполняется начальная
validation: неизменённый источник тоже может остаться лучшим чекпоинтом.
GFlow использует teacher curriculum длительностью **10 эпох**.

На один источник приходится **121 запуск**:

| Ветка | Сетка | Запусков |
|---|---|---:|
| SFT | Только supervised loss | 1 |
| GFlow | 4 награды × 3 степени × 2 rho × TB/DB/SubTB | 72 |
| CE | 4 награды × 3 степени × 2 rho × 2 способа семплирования | 48 |

Награды: `sasrec`, `interaction`, `similarity` и произведение всех трёх.
Степени: **0.25, 1, 16**; rho: **0.1, 1**. Степень применяется к составной
награде один раз. Rho задаёт целевое отношение норм градиентов дополнительного
и SFT-лосса; коэффициент дополнительного лосса калибруется на исходном SFT-only.
Для каждой новой GFlow/CE-ячейки λ вычисляется заново на выбранных SFT-only весах,
до первого обновления optimizer, и сохраняется в её собственном `calibration.json`.
Калибровка предыдущего эксперимента не импортируется. При восстановлении прерванной
ячейки сохраняется её уже вычисленная λ; CE также может переиспользовать свою
калибровку, если процесс прервался до сохранения первого checkpoint.

У GFlow **K=3** отрицательных кандидата. В CE используются **три независимых
выборки из каталога с возвращением**: повторы и выбор целевого item допустимы.
Это сохраняет распределение `q = R / sum(R)`; исключение target изменило бы
обучающую цель. Режимы CE: `reward` (выборка непосредственно из q) и
`curriculum_smooth_is` (плавное изменение proposal с поправкой q/proposal).
Переход CE curriculum занимает **5 эпох**, доля полного q в proposal
составляет **epsilon = 0.1**.

## Источники и воспроизведение протокола

По умолчанию выбраны **9 источников, 1089 запусков**:

| source_id | Исходный SFT-only |
|---|---|
| `tiger_beauty` | `finetuned`, Beauty |
| `tiger_instruments` | `finetuned`, Instruments |
| `tiger_yambda50_matched` | `finetuned_matched`, полный last128 |
| `tiger_yambda500_matched_r15` | `finetuned_matched_r15`, 15 целей из last128, subset seed 42 |
| `gpt2_beauty` | Amazon dense-prefix, Beauty |
| `gpt2_instruments` | Amazon dense-prefix, Instruments |
| `gpt2_beauty_2023` | Amazon dense-prefix, Beauty2023 |
| `gpt2_yambda50_trial36` | Trial 36, полный last128 |
| `gpt2_yambda500_trial4_sampled50` | Trial 4, 50 целей из last128, subset seed 42 |

Пути и идентичность источников задаёт [sft_source_protocol.py](sft_source_protocol.py).
Основные веса читаются из `checkpoints/exp2/loo_split/sft-finetuned/<model>/<dataset>/best.pt`.
Для GPT2 Yambda50 путь включает папку `last_128`,
для GPT2 Yambda500 — `sampled_50`. Вес используется,
только если `provenance.json` подтверждает нужные источник и seed, а SHA-256 весов
совпадает с записанным. Ссылки на другие seed этого же источника используют
основную модель; в путях, результатах и идентификаторах записывается её
фактический seed, а одинаковые после подстановки задания объединяются.
Метаданные исходного запуска читаются рядом с основными весами; дополнительные
записи берутся из замороженного JSON. Идентичность источника определяется
путём выбранных весов, их хешем и хешами метаданных и протокола.

Подготовка использует архитектуру, семантические ID, построение префиксов,
подмножество целей и параметры оценки выбранного источника. Дополнительные
записи протоколов заморожены в `source_protocols.json`. Сами веса,
метаданные источника, датасеты, tokenizer/RQ-VAE и SASRec teacher должны быть
доступны по путям проекта. Несовпадение источника вызывает ошибку; подстановки
начального чекпоинта нет. Исходные файлы не перезаписываются.

TIGER Beauty2023 и TIGER Yambda500 полного matched-протокола не включены
в выборку по умолчанию. Для Beauty2023 доступны основные веса seed42 и sidecar,
но полный исходный конфиг, результат и замороженный протокол не предоставлены.
Полный matched Yambda500 недоступен
как текущий основной источник; для выбранного r15 нужен явный
`--source-ids tiger_yambda500_matched_r15`.

```bash
python scripts/exp8-from-sft/finetune_from_sft.py --phase prepare --list
python scripts/exp8-from-sft/finetune_from_sft.py --check-sources
python scripts/exp8-from-sft/finetune_from_sft.py --count
python scripts/exp8-from-sft/finetune_from_sft.py --list
```

`--count` и `--list` используют только стандартную библиотеку Python и не
загружают данные, веса или Torch. Индексы зависят от переданных фильтров.

## Запуск на кластере

Из корня репозитория:

```bash
module load python
conda activate flowrec
export PYTHON_BIN="$CONDA_PREFIX/bin/python"
export PATH="$CONDA_PREFIX/bin:$PATH"
bash scripts/scheduler/submit_finetune_from_sft.sh --dry-run --prepare-only
bash scripts/scheduler/submit_finetune_from_sft.sh --prepare-only
```

Первый вызов только печатает команды. Второй проверяет наличие и метаданные
всех выбранных источников до первой отправки, затем ставит задачи в scheduler.
Python закреплён абсолютным путём; его `bin` ставится первым в `PATH`.
Worker перед расчётом выводит фактические пути Python и Torch.

Можно выбрать модель, датасеты или ветки без редактирования файлов:

```bash
bash scripts/scheduler/submit_finetune_from_sft.sh --dry-run --prepare-only -- \
  --models gpt2 --datasets beauty instruments --arms sft gflow ce
```

Подготовка разделена на CPU и GPU. CPU-задачи строят `interaction` и
`similarity`; GPU-задачи — `sasrec` и оценку исходного SFT-only. Режим
`--prepare-only` отправляет только эти задачи, без обучения. Это особенно важно
для Yambda500: подготовка interaction-кеша может занимать несколько часов.
GPU не резервируется на это время. В каждом профиле GPU-фаза следует за CPU-фазой:
она использует уже проверенную идентичность обучающих данных.

После успешного завершения **всех** подготовок отправляйте обучение вручную
по блокам: `--train-block 1`, после его завершения — `--train-block 2` и т. д.
Одна конфигурация соответствует одной scheduler-задаче. Размер блока
по умолчанию 121 (`--block-size`); при полной сетке это один исходный чекпоинт.
Всего по умолчанию 9 блоков, без TIGER Beauty/Instruments — 7 блоков.
Нумерация сначала объединяет сетки выбранных профилей в порядке `--profiles`
(по умолчанию `small large yambda`), внутри профиля сохраняет порядок источников
из `--source-ids`. Используйте одинаковые фильтры, порядок профилей и размер
блока при всех отправках; номер блока отображается и в `--dry-run`.

Перед обучением отдельная проверка читает только метаданные готовности кешей
**всех выбранных источников**. Она не загружает данные или Torch на login-узле;
полную проверку совместимости выполняет каждая вычислительная задача.
Submit-скрипт также проверяет очередь через `worker-status --array` по всем аккаунтам:
имеющиеся задачи плюс новые не должны превышать 500. `MAX_SUBMITTED_JOBS`
может только снизить этот порог. Ошибка чтения очереди блокирует отправку.
Ограничение `%N` регулирует только параллельность и не уменьшает число
отправленных задач: [документация scheduler](https://scheduler.schedmd.com/job_array.html).
Следующий блок не ставится, пока в очереди есть подготовка или обучение exp8.
Другие эксперименты учитываются в лимите и могут продолжать работать.
Для независимого поднабора можно явно задать `--queue-scope profiles`:
тогда ожидание касается только выбранных непустых профилей (`--profiles`).
Подготовка всех выбранных источников и общий лимит 500 проверяются.
Задачи разных источников внутри одного профиля остаются взаимно блокирующими.
Без этого флага учитываются все задачи exp8.

Для запуска без уже работающих TIGER Beauty/Instruments:

```bash
sources=(
  gpt2_beauty gpt2_instruments gpt2_beauty_2023
  gpt2_yambda50_trial36 gpt2_yambda500_trial4_sampled50
  tiger_yambda50_matched tiger_yambda500_matched_r15
)
bash scripts/scheduler/submit_finetune_from_sft.sh --prepare-only -- --source-ids "${sources[@]}"
# Только после завершения всех подготовок:
bash scripts/scheduler/submit_finetune_from_sft.sh --train-block 1 -- --source-ids "${sources[@]}"
# После завершения блока 1 повторить последнюю команду с номером 2, затем 3..7.
```

| Блок | Источник при указанном порядке `sources` | Задач |
|---:|---|---:|
| 1 | GPT2 Beauty | 121 |
| 2 | GPT2 Instruments | 121 |
| 3 | GPT2 Beauty2023 | 121 |
| 4 | GPT2 Yambda50, trial36 | 121 |
| 5 | GPT2 Yambda500, trial4 sampled50 | 121 |
| 6 | TIGER Yambda50, matched | 121 |
| 7 | TIGER Yambda500, matched_r15 | 121 |

Если часть источников ещё готовится, готовые источники можно обучать отдельно,
сохранив номера из этой таблицы:

```bash
bash scripts/scheduler/submit_from_sft_source_block.sh 1
# После завершения предыдущего обучающего блока:
bash scripts/scheduler/submit_from_sft_source_block.sh 2
```

Аналогично выбираются номера 3..7; каждый вызов отправляет только один массив
из 121 конфигурации. К команде можно добавить `--dry-run`. Номер источника
здесь фиксирован: пропуск блока 5 не перенумеровывает блоки 6 и 7.
Wrapper выбирает ровно один `--source-ids` и вызывает основной helper с
локальным `--train-block 1 --queue-scope training`; scheduler-индексы внутри
этого выбранного источника равны 0..120. Каталоги результатов и идентичность
конфигураций совпадают с полной сеткой семи источников.

Режим `--queue-scope training` разрешает продолжающуюся подготовку других
источников, но ждёт завершения всех уже поставленных обучающих задач exp8.
Неизвестные задачи exp8 также блокируют отправку. Готовность CPU/GPU-кешей
выбранного источника проверяется до отправки; незавершённый источник запустить
нельзя. Все подготовительные задачи и задачи других экспериментов учитываются
в общем лимите 500. Этот режим допустим только для обучения, не для
`--prepare-only`. Режимы `all` и `profiles` также проверяют очередь.
Не отправляйте повторно подготовку профиля, пока его задачи присутствуют в очереди.

### Дополнительные SFT-only и CE для TIGER Beauty/Instruments

Для отдельных SFT-only и CE веток выберите соответствующие параметры.
Это **98 конфигураций: 2 SFT-only и 96 CE**.
LR остаётся 3e-5, seed 42; CE использует 3 выборки, 4 комбинации наград,
степени 0.25/1/16, rho 0.1/1 и 2 способа семплирования.

```bash
bash scripts/scheduler/submit_finetune_from_sft.sh \
  --prepare-only --queue-scope profiles --profiles small -- \
  --source-ids tiger_beauty tiger_instruments --arms sft ce \
  --reuse-tiger-gflow-caches

# После успешного завершения обеих фаз подготовки этих двух источников:
bash scripts/scheduler/submit_finetune_from_sft.sh \
  --train-block 1 --queue-scope profiles --profiles small -- \
  --source-ids tiger_beauty tiger_instruments --arms sft ce
```

Первая команда отправляет 4 подготовительные задачи (2 CPU + 2 GPU), вторая —
один блок из 98 обучающих задач с параллельностью 8. GFlow-задачи
`flowrec_gflow_tiger_from_sft` не блокируют эти отправки; все их элементы
учитываются в лимите 500. Подготовка/обучение exp8 в `large` и `yambda` могут
продолжать работать. Если уже есть задачи `from_sft_small_*`, дождитесь их
завершения.

`--reuse-tiger-gflow-caches` использует уже вычисленные сырые факторы из
`artifacts/exp4-reward_ablation/gflow_tiger_from_sft/<dataset>/reward_factors/`.
CPU-задача проверяет совместимость всех строк, каталога и конфигураций,
копирует готовые `factors.pt` в exp8 и создаёт недостающий снимок данных
`prepared_data`. Факторы **не пересчитываются**; старые payload/manifest не
изменяются, поэтому работающий GFlow продолжает использовать свои файлы.
Количество выборок, rho, степень награды и лосс применяются поверх сырых
факторов и не требуют нового кеша. При несовместимости или отсутствии кеша
reuse-режим завершается с ошибкой, без автоматического пересчёта.

GPU-задача после импорта оценивает исходный SFT-only checkpoint для baseline
exp8. Метрики baseline должны иметь описание оценки и хеши источника;
совместимые готовые подготовки exp8 повторно не вычисляются.

Manifest исходного кеша может не содержать хешей данных и teacher.
Импорт фиксирует SHA-256 исходного payload/manifest, сравнивает все строки
user/target/token/timestamp, SASRec item table, similarity codebook и
выборочно проверяет SASRec hidden и interaction reward на текущих входах.
Ограничение проверки записывается в provenance; это не полная
повторная оценка каждого reward. При известных заменах данных или teacher
после построения исходного кеша нужен отдельный кеш, а не reuse.

Эти команды продолжают исходные SFT-only веса и используют ту же
обработку данных, выполняя **протокол exp8**. В отдельном GFlow-протоколе
K=10, batch 32×64, валидация каждую эпоху и patience 5; в контролях exp8
batch 256×8, валидация каждые 5 эпох и patience 10, у CE 3 выборки.
Эффективный batch одинаковый (2048), однако расписание проверок и остановки
различается. В отдельной GFlow-сетке также присутствует степень 4, которой нет
в сетке exp8. Для строгого сравнения методов эти различия нужно учитывать.

CPU-фаза также сохраняет проверенные обработанные данные в
`artifacts/exp8-from-sft/<source_id>/sft_seed_42/prepared_data/`.
GPU-подготовка и все обучающие ячейки загружают этот снимок, поэтому тяжёлая
обработка сырых данных не повторяется на каждой GPU. При отсутствующем или
несовместимом снимке запуск останавливается и требует CPU-подготовку.
Для GPT2/Yambda CPU-фаза также строит соответствие ID каталога SASRec teacher.
Обе фазы подготовки фиксируют SHA-256 этого файла; его изменение или удаление
блокирует использование подготовленных кешей и запуск обучения.

| Профиль | Данные | GPU обучения | Лимит одной ячейки | Одновременно |
|---|---|---|---|---:|
| `small` | Beauty, Instruments | V100 32 GB (`type_a` или `type_c`) | 12 ч | 8 |
| `large` | Beauty2023 | A100 80 GB (`type_e`) | 23 ч 59 мин | 2 |
| `yambda` | Yambda50M, Yambda500M | A100 80 GB (`type_e`) | 23 ч 59 мин | 1 |

Выделяется одна GPU и четыре CPU на обучение; CPU-подготовка использует
два CPU без GPU. Для CPU-подготовки всех профилей выбран `type_d`
(узлы без GPU); при необходимости тип меняется через
`PREFIX_PREPARE_CPU_CONSTRAINT`. `--mem` и номера узлов не используются. Лимиты времени
опираются на предыдущие запуски и требуют уточнения после первых новых
результатов; пиковая host RAM нового этапа ещё не измерена.
[Правила HSE](https://cluster.example.org/llms.txt),
[запуск и планирование](https://cluster.example.org/instructions/run).

Все настройки и переменные окружения перечислены в `--help` submit-скрипта.
Например:

```bash
ACCOUNT="${PROJECT_ACCOUNT:?Set PROJECT_ACCOUNT}" SMALL_MAX_PARALLEL=4 \
  bash scripts/scheduler/submit_finetune_from_sft.sh --train-block 1 --profiles small
```

## Повторный запуск и результаты

### Восстановление Yambda после таймаута CPU-подготовки GPT-2 500M

Для массива с порядком `tiger_yambda50_matched`, `tiger_yambda500_matched_r15`,
`gpt2_yambda50_trial36`, `gpt2_yambda500_trial4_sampled50` предусмотрен отдельный
recovery helper. Он требует состояния `COMPLETED` у CPU-элементов 0/1/2,
`TIMEOUT` у элемента 3 и `PENDING` у всех четырёх GPU-элементов. Он проверяет
маркеры и снимки завершённой CPU-подготовки, а также лимит 500 задач до отправки.
Укажите идентификаторы массивов через `CPU_ARRAY_ID` и `GPU_ARRAY_ID`.

```bash
bash scripts/scheduler/recover_from_sft_yambda.sh \
  --cpu-array "${CPU_ARRAY_ID:?Set CPU_ARRAY_ID}" \
  --gpu-array "${GPU_ARRAY_ID:?Set GPU_ARRAY_ID}"
```

Будет отправлена одна CPU-задача для GPT-2 Yambda500 sampled50
(`type_d`, 2 CPU, 0 GPU, массив `0%1`, лимит 8 часов). Для GPU-элементов
0/1/2 снимается зависимость от завершённых CPU-элементов; элемент 3 получает
`afterok` от повторного CPU-запуска. Задачи не отменяются.
При несовпадающих состояниях скрипт завершается до изменения очереди.
`--dry-run` печатает команды; `--cpu-time` меняет лимит повторного запуска.
Восемь часов — начальный бюджет восстановления, не измеренная длительность.

Если повторная CPU-задача тоже завершилась с ошибкой, передайте её ID отдельно:

```bash
bash scripts/scheduler/recover_from_sft_yambda.sh \
  --cpu-array "${CPU_ARRAY_ID:?Set CPU_ARRAY_ID}" \
  --gpu-array "${GPU_ARRAY_ID:?Set GPU_ARRAY_ID}" \
  --retry-cpu-array "${RETRY_CPU_ARRAY_ID:?Set RETRY_CPU_ARRAY_ID}"
```

В этом режиме helper проверяет, что повторный массив содержит только элемент
0, завершился неуспешно и по записанной scheduler-команде готовил именно GPT-2
Yambda500 sampled50. Для этого в `worker-accounting` нужен доступный `SubmitLine`.
Также проверяются сохранённый `prepared_data/manifest.json`, идентичность
источника и наличие/размер/mtime файлов снимка; чтение десятков гигабайт на
login-узле не выполняется. Полную совместимость проверяет обычный runtime
уже внутри CPU-задачи. Если снимок отсутствует, helper останавливается до
отправки нового задания.

Только GPU-элемент 3 должен оставаться `PENDING`: он получит зависимость
`afterok` от повторного CPU-массива. GPU-элементы 0/1/2 могут уже выполняться или
завершиться — их зависимости и состояния не меняются. Проверка лимита 500
задач и защита от параллельной CPU-подготовки сохраняются. Готовый снимок и
полностью записанные reward-компоненты переиспользуются, но незавершённый
interaction-компонент пока приходится считать с начала: промежуточного
восстановления по батчам у него нет.

Повторная подготовка получает `--history-build-chunk-size 100000`:
исходная функция построения историй вызывается на частях таблицы, а не на
всех префиксах одновременно. Это ограничивает промежуточный `merge/groupby`;
итоговый datamodule содержит все примеры. Полный matched audit
остаётся обязательным. Тесты сравнивают значения, порядок, типы и хеши с
исходным способом. Файлы, входящие в fingerprint ранее подготовленных
снимков, не изменяются; совместимые снимки можно переиспользовать.

Recovery helper задаёт `--traceback-interval 0`: периодический вывод стеков
отключён, отметки этапов и прогресс батчей остаются в stdout. По запросу
`--traceback-interval 300` включает снимок стека каждые пять минут через
обычный Python-поток.
CLI-параметры `--traceback-interval` и `--history-build-chunk-size` по
умолчанию равны нулю; helper отдельно включает обработку историй частями.

После таймаута повторная отправка **того же номера блока** использует те же каталоги: завершённые
ячейки пропускаются, незавершённые продолжаются с сохранённого состояния.
Во всех трёх ветках checkpoint сохраняется атомарно каждые **100 обновлений
оптимизатора**; интервал задаётся `--checkpoint-every-updates`.
Работа после последнего checkpoint выполняется повторно. Повторную отправку
делайте после завершения прежних задач для этих же ячеек.

Если обе подготовки уже успешно завершены:

```bash
bash scripts/scheduler/submit_finetune_from_sft.sh --train-block 1
```

Флаги модели, источников и данных должны совпадать с подготовкой. Worker
проверяет совместимость подготовленных артефактов; ошибку нельзя заменить
тихой перестройкой кешей внутри обучающей GPU-задачи.

Результаты сохраняются в `experiments/exp8-from-sft/`, кеши — в
`artifacts/exp8-from-sft/`, scheduler-логи — в `scheduler_logs/from_sft-<job>_<task>.*`.
`prepared_data/` содержит объёмный рабочий кеш, а не метрики: при скачивании
результатов его можно исключить. На кластере он нужен для последующих
запусков с `--train-block` и продолжения незавершённых ячеек.
Режим `--smoke` использует отдельные подкаталоги. Команды `--list`, `--count`
и `--dry-run` сами по себе ничего в очередь не отправляют.
